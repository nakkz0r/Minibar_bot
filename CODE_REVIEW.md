# Код-ревью: Minibar Bot 🏨

*Ревью от 09.08.2026. Проверены: `bot.py`, `r2_storage.py`, `requirements.txt`, `.env.example`, `.gitignore`, настройки git.*

## Общий вердикт

Бот рабочий, и по структуре — прям достойно: aiogram 3 с FSM, облачный бэкап вынесен в отдельный модуль, сетевые вызовы R2 не блокируют бота (`asyncio.to_thread`), SQL-запросы параметризованы (SQL-инъекций нет). Основа хорошая.

Но есть **одна критичная дыра в безопасности** и набор багов, из-за которых отчёты могли тихо теряться, а данные — искажаться. Всё, что можно исправить кодом, **уже исправлено** в обновлённых файлах. Осталось два действия руками — см. «Что сделать срочно».

## 🔴 Критично №1: токен бота лежит в открытом доступе в интернете

Настоящий токен бота закоммичен в **публичный** репозиторий `github.com/nakkz0r/Minibar_bot` — сразу в двух местах:

- `bot.py`, строка 31 — токен вшит в код как значение «по умолчанию»;
- `.env.example`, строка 2 — в шаблон вписаны реальные значения вместо заглушек.

**Чем грозит:** любой человек в интернете может забрать токен и полностью управлять ботом — слать сообщения от его имени, перехватить рабочий процесс отеля, сломать смену. Там же засветились ID рабочего чата и личные Telegram ID (это менее страшно, но неприятно).

### Что сделать СРОЧНО (5 минут)

1. Открыть **@BotFather** → `/mybots` → выбрать бота → **API Token** → **Revoke current token**. Старый токен мгновенно перестанет работать (это главное).
2. Новый токен вписать **только** в локальный файл `.env` и в настройки хостинга (Render → Environment → `BOT_TOKEN`). Больше никогда не вставлять его в код или `.env.example`.
3. Рекомендую сделать репозиторий приватным: GitHub → Settings → внизу Danger Zone → Change visibility → Private. (Токен остаётся в старых коммитах; после отзыва он бесполезен, но чат-ID и юзернеймы всё ещё видны.)

Хорошая новость: ключи от Cloudflare R2 **не** утекли — в шаблоне на их месте были заглушки. `.env` в git не попадал (`.gitignore` настроен верно).

**Исправлено в коде:** секреты убраны полностью. Теперь без `BOT_TOKEN` / `REPORT_CHAT_ID` бот не запустится и понятным текстом скажет, чего не хватает.

## 🔴 Критично №2: `/clear` стирал всё без подтверждения — вместе с бэкапом

Было (bot.py:269–286): одно сообщение `/clear` — и все данные смены удалены, а следом бот **сразу перезаписывал облачный бэкап пустой базой**. Промахнулся пальцем — данные не вернуть вообще.

**Исправлено:** `/clear` теперь спрашивает подтверждение кнопками, а перед очисткой сохраняет архив смены в R2 (`backups/minibar_<дата_время>.db`). Ошиблись — данные можно поднять из архива.

## 🔴 Критично №3: отчёты могли «тихо» не доходить, а бот говорил «успешно»

Три независимые причины, все приводили к одному: отправка в рабочий чат падала, ошибка глоталась `except`-ом (bot.py:466–467), сотрудник видел «ანგარიში წარმატებით გაიგზავნა!», супервайзеры — ничего.

1. **Спецсимволы в имени сотрудника.** Имя из Telegram вставлялось в HTML-разметку как есть (bot.py:437). Если в имени есть `<`, `>` или `&` (эмодзи-ники, «👑 <Anna>») — Telegram отклоняет сообщение целиком.
2. **Файл вместо фото.** Бот принимал любой документ как «фото» (bot.py:473–480), но отправить document-file_id через `send_photo` нельзя — Telegram возвращает ошибку. Плюс как «фото» проходил вообще любой файл, хоть PDF.
3. **Лимиты длины.** Отчёт содержит список всех проверенных номеров. При ~60+ номерах текст превышает лимиты Telegram (1024 символа для подписи к фото, 4096 для сообщения) — отправка падает. То же с `/status`.

**Исправлено:** все данные пользователей экранируются; картинки-файлы отправляются через `send_document`, не-картинки вежливо отклоняются; длинные сообщения режутся на части; при реальном сбое сотрудник теперь видит честное «данные сохранены, но отчёт в чат не ушёл — сообщите администратору».

## 🟢 Мелочи (исправлены)

- Код миграции БД был скопирован в 4 местах — теперь один раз в `init_db()`.
- Номера сортировались как текст (1010 раньше 605) — теперь как числа.
- Версии зависимостей не были зафиксированы — закреплены (`aiogram>=3.7,<4` и т.д.).
- В отчёте и `/audit` теперь видно, **кто и когда** проверил номер (время грузинское, UTC+4) — раньше имя нигде не сохранялось, аудит был анонимным.
- При остановке бота — финальный бэкап в R2.
- У R2-клиента появились таймауты и повторы: зависший сетевой вызов больше не вешает бэкап навсегда.
- `parse_mode="HTML"` задан один раз по умолчанию, а не в каждом вызове.

## Что НЕ трогал (и почему это нормально)

- **SQLite + R2 вместо «настоящей» БД** — для одного отеля и нескольких горничных это разумный выбор, Postgres тут не нужен.
- **Состояния диалога в памяти** — при рестарте сервера незавершённые проверки сбрасываются, сотрудник просто жмёт `/start` заново. Для этого масштаба ок; Redis был бы лишним усложнением.
- **Все тексты и логика статусов** — как были, персонал разницы не заметит.
- **Опечатка `Cola Clasic`** (правильно Classic) — оставил намеренно: это ключ, под которым данные лежат в базе. Исправление потребует маленькой миграции — скажите, сделаю.
- `/status` доступен всем (хотя комментарий в `.env.example` обещал «только супервайзерам») — оставил открытым, как было в коде; ограничить — одна строка.

## Как выкатить обновление (шаги для друга)

1. **Сначала** — отозвать токен у @BotFather и вписать новый в `.env` и в Render (см. Критично №1).
2. В папке проекта: `pip install -r requirements.txt --upgrade` (нужен aiogram 3.7+; проверено на 3.30).
3. Запустить локально и убедиться, что в логах есть `Starting Telegram Bot polling...`.
4. `git add -A` → `git commit -m "Security & bugfix after code review"` → `git push`. Render передеплоит сам (или Manual Deploy).
5. Быстрый прогон: `/start` → номер → статус → фото; `/status`; `/audit 605`; `/clear` (теперь спросит подтверждение).

Обновлённый код прогнан автопроверками: импорт на aiogram 3.30, миграция старой базы (новые колонки добавляются к существующим данным без потерь), подсчёт продукции, разбивка длинных сообщений, экранирование, снимок БД — всё зелёное.
